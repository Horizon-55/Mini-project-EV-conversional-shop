# Політика дублювання даних та узгодженості між мікро-БД

## 1. Концепція поліглотного збереження та дублювання
У мікросервісній архітектурі діє правило **Database-per-Service**: кожен мікросервіс має власну автономну базу даних. Прямі міжсервісні JOIN-запити на рівні SQL або міжсервісні зовнішні ключі (Foreign Keys) **суворо заборонені**, оскільки вони створюють жорстку зв'язність (tight coupling) та руйнують незалежність розгортання.

Щоб уникнути повільних і ненадійних синхронних HTTP/gRPC викликів при кожній операції читання (патерн *Chatty Services* / *Distributed Monolith*), застосовується **контрольоване дублювання даних**.

## 3. Чому неприпустимий "Dual Write"?
**Dual Write** — це антипатерн, за якого застосунок одночасно в одному коді намагається записати дані у дві різні бази даних без розподіленої транзакції:
```csharp
// АНТИПАТЕРН DUAL WRITE:
await catalogDbContext.SaveChangesAsync(); // Успішно
await orderingDbContext.SaveChangesAsync(); // Помилка мережі -> Бази розсинхронізовані назавжди!
```

**Правильний підхід (як вимагає методичка та eShop):**
1. Сервіс-власник (`Catalog Service`) записує зміну у власну БД.
2. Сервіс-власник публікує доменну подію (Outbox Pattern / Message Broker).
3. Сервіс-підписник (`Ordering Service` чи `Reviews Service`) отримує повідомлення та оновлює свою локальну копію даних.
